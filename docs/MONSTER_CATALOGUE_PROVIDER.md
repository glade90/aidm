## Implementation boundaries

aidm/catalogue.py defines SqlServerReader(connection_factory), MonsterCatalogue, MonsterTestScenarios, frozen MonsterSnapshot/TestScenarioDefinition/TestCaseDefinition, ActorSeed and CombatRosterHandoff. The SQL connection is injected; no SQL Server dependency or network on import and no writes anywhere. The SQL reader executes parameterized fixed SELECTs, enforces bounds and closes connections; caller MUST use a real SELECT-only principal.

Normal monster lookup filters Active=1 + SourceStatus=Approved. An explicit local test-only flag permits inspecting inactive SourceChecked rows but NEVER marks them Approved/Active, nor permits running them. Unknown rulesets, absent/ambiguous dates, bad types and missing source stats are rejected/not playable. All metadata/NULL values and natural-language combat-versus-encounter feature separation are retained.

Normalized test scenario/case reader validates uniqueness, statuses, JSON, foreign-case identity and bounds. Incomplete and ReadyForExecution=0 tests may only be inspected through explicit test-only mode. It does not execute tests or turn a Specified row into UAT PASS.

build_test_handoff requires separate trusted mechanics-verification reference, approved version-pinned species, Ready scenario and Ready case definitions, fixed actor identities/starting HP (never generated by catalogue), and unique party/monster IDs. If a scenario specifies actor species_record_date, the provider now queries that exact RecordDate and rejects missing, conflicting, or partial pins for the same species. Without an explicit date, it still requires one uniquely approved active version and immediately pins that returned date. The frozen Combat-facing profile never contains SpecialEncounterFeatures.

NEW 26 NOVEMBER: aidm/catalogue_combat.py provides prepare_prototype_encounter(handoff, authored_template=..., mechanics_supported=...). The trusted caller supplies an AUTHOR-VERIFIED stationary encounter template with matching actual party IDs/HP, monster IDs/equipped weapon, scenario scene-facts boolean approved_for_test_bootstrap=True, separate rules receipt and explicit mechanics_supported verifier. The adapter replaces the existing Combatant's actual HP/AC/HD/SaveAs and MonsterDefinitionSnapshot's versioned stats/source ref using the catalogue; no SQL connection is transferred to Combat. It cannot invent location, weapon, initiative, monster HP or scene. The engine in this slice is not a generic monster-rule interpreter: any nonempty SpecialAttacksFeatures or nonordinary monster role **always blocks**, even if the verifier says yes. Distinct instance HP can share the same source-version identity. Noncombat species behaviours (negotiation, stand-off, etc.) remain outside Combat.

CombatSessionService(prototype_encounter=prepared_encounter) accepts ONLY an explicitly preconstructed immutable EncounterDefinition at trusted Python construction time, and reuses its source-pinned in-memory values for START and RESET. This seam cannot query SQL at runtime: it receives only the typed encounter, NOT a provider, database cursor or connection. No new user-facing fixture IDs or API contracts are admitted; B1 HTML remains disabled, and the running fixture is labelled TEST_ONLY. Without injection, original canonical synthetic 3v3 remains unchanged. The current test-only composition is NOT DES-020 authoritative Encounter orchestration, not production source approval, and is NOT permission to present five B1 fixtures as READY.

public_monster_asset projects only a revealed Approved+Active species name and safe local assets paths. Source prose, hidden abilities, HP, DB connection errors and secrets are never in that view.

## 26 November SQL smoke failure: safe diagnostic preflight

Owner ran a live PEQUOD smoke at source 3c2ad6f8 and all four monster lookups and the Orc test scenario returned generic `CatalogueUnavailable`. Because `SqlServerReader` intentionally suppresses the raw pyodbc exception to prevent secret leakage into player/server surfaces, this does NOT prove missing tables: wrong database, ODBC driver/host, login, permissions and missing v0.4 schema columns are all possible.

From `davos` head at or later than `6c31d619e0cf7149843b5f7afe10e92287a232fa`, `python -m aidm.catalogue_smoke` runs a developer-only **read-only preflight** before the four lookups. It checks connectivity with `SELECT DB_NAME()` (must be `DnD`), then `SELECT TOP (0)` all required v0.4 Monster / TestScenario / TestCase columns. Safe output is only `ODBC_CONNECT`, `DATABASE_CONTEXT`, `RULES_MONSTER`, `TEST_SCENARIO`, `TEST_CASE`, `OK/BLOCKED`, and a sanitized five-character SQLSTATE category; no original driver text, server, user, password or connection string is displayed. Confirm the configured principal has SELECT-only authority **before** running. No schema migrations or writes are performed.

Possible results:
- `ODBC_CONNECT: BLOCKED [08001]`: server/network/ODBC connection failure; `[28000]`: authentication/SQL login; `[IM002]`: missing ODBC driver/DSN; `[HYT00]`: timeout.
- `DATABASE_CONTEXT: BLOCKED`: connection's default `DATABASE` is not `DnD`; correct the private connection string, not application SQL.
- `RULES_MONSTER: BLOCKED [42S02]`: table absent/not visible; `[42S22]`: required v0.4 column missing; `[42000]`: SQL permission or syntax. Same for both Test tables.
- `SCHEMA_AND_SELECT_OK`: table accessible and all expected columns present; this is not approval of the row status or a comprehensive functional validation.
