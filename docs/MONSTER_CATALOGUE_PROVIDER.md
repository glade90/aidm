## Implementation boundaries

aidm/catalogue.py defines SqlServerReader(connection_factory), MonsterCatalogue, MonsterTestScenarios, frozen MonsterSnapshot/TestScenarioDefinition/TestCaseDefinition, ActorSeed and CombatRosterHandoff. The SQL connection is injected; no SQL Server dependency or network on import and no writes anywhere. The SQL reader executes parameterized fixed SELECTs, enforces bounds and closes connections; caller MUST use a real SELECT-only principal.

Normal monster lookup filters Active=1 + SourceStatus=Approved. An explicit local test-only flag permits inspecting inactive SourceChecked rows but NEVER marks them Approved/Active, nor permits running them. Unknown rulesets, absent/ambiguous dates, bad types and missing source stats are rejected/not playable. All metadata/NULL values and natural-language combat-versus-encounter feature separation are retained.

Normalized test scenario/case reader validates uniqueness, statuses, JSON, foreign-case identity and bounds. Incomplete and ReadyForExecution=0 tests may only be inspected through explicit test-only mode. It does not execute tests or turn a Specified row into UAT PASS.

build_test_handoff requires separate trusted mechanics-verification reference, approved version-pinned species, Ready scenario and Ready case definitions, fixed actor identities/starting HP (never generated by catalog) and unique party/monster IDs. Returns a typed immutable CANDIDATE for future server-side Encounter→Combat, not a live engine session. The Combat-facing profile never contains SpecialEncounterFeatures. More runtime binding is needed before user-facing encounter readiness; DES-020 owns real encounter dispatch, DES-001.7.12.1 supplies first five B1-source fixtures. No direct DB access is added to Combat/Browser/DM.

public_monster_asset projects only a revealed Approved+Active species name and safe local assets paths. Source prose, hidden abilities, HP, DB connection errors and secrets are never in that view.
