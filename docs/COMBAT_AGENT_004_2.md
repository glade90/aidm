# DES-004.2 — Model-backed specialist CombatAgent (first Sprint 3 increment)

**Status:** Developer candidate, not BON Functional UAT or release approval.

## Why

CombatAgent is the specialist interpreter for combat-specific words and the narrator of *verified* Engine events. The one player-facing DM delegates through the **existing** Browser → Meta `/api/turn` → DM → CombatSessionService gateway. CombatSessionService is the Python coordinator; `CombatEngine` retains sole authority for dice, legal actions, HP and journal. There is no second DM LLM call to rewrite the specialist narrative.

## Included

- `aidm/combat/round_agent.py` introduces `CombatRoundAgent(Braider)` and `ResponsesBraiderRuntime`. The runtime reuses the existing opted-in `OpenAIResponsesPolicy` transport and its credential/no-store/timeout boundaries. It does not create another provider client or require network access by default.
- An `INTENT` call submits the **exact original utterance**, pending actor ID, an allowlist of legal targets, and bounded *trusted player-visible* context (current round/version, visible actor roster, approved rules-profile ID and a short redacted event history). A model response is parsed strictly as a nonauthoritative pair `(kind, target_id)`; unknown mechanics, malformed JSON and illegal targets cannot become Engine commands. Existing exact numeric/HOLD shortcuts retain deterministic priority.
- For this policy, narration is invoked **once when a mechanically completed round/terminal outcome has been journaled**. Only player-safe Engine-projected events are supplied. Replayed requests and `VIEW_LOG` do not cause additional narration invocations. The deterministic public event log and rule outcomes remain primary; the optional model prose is labelled non-authoritative. On failure, the verified event narrative already generated by the existing gateway remains available.
- Offline mode continues to use `ScriptedIntentPolicy` and `CombatAgent`'s original synthetic `mock_combat_intent` path. Existing explicitly injected `IntentPolicy` fakes remain supported.
- The provider is injected through the existing `AIDM_LIVE_LLM=1`, `AIDM_LLM_MODEL`, `OPENAI_API_KEY` configuration in development mode. Do not commit a real key or enable network in test/CI. Live demonstration is **not verified** merely because offline model tests pass.

## Known limitations and separate Stories

- This is the **bounded first specialist vertical slice** on the existing **per-human-decision** browser interface. It does **not** implement the separately owned one-party-declaration-per-round planner, cross-round spell/weapon intent inheritance, bounded whole-round validation/repair or mid-round exceptional checkpoint pause/resume. Those need the additional BON/ALEK-governed Build and must not be described as included here.
- `spatial_graph` explicitly says `NOT_INJECTED_FIRST_SLICE`; no invented coordinate, distance or line-of-sight facts. Actual authored graph and dead-target nearest-survivor fallback are DES-018.2 / later integration requirements, not implicitly delivered.
- No monster-specific source-rule interpretation (001.7.4), generic condition bridge (006.5), Bookkeeper/DB (017), expanded spell/missile/morale, monster special attacks or location/corpse tracking.
- Output constraints are enforced for typed **intent**, but free-text model narration cannot be mathematically guaranteed factually faithful solely by a prompt. Always expose the unchanged verified event journal; model prose is clearly nonauthoritative and must be independently accepted by BON UAT.
- No real-provider test performed by COSTA on PEQUOD from this environment; an owner-controlled live-mode full encounter with provider evidence is required before Functional UAT PASS.
